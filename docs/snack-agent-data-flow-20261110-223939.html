C

服务端编排：模型提议，代码组装并执行

请求入口。 主路由校验非空 input，并去除首尾空白。 sessionId 和可选 retryLimit 传入执行器。 每次运行生成新的 requestId。 未传会话 ID 时，再生成新的 sessionId。

上下文加载。 执行器并行读取 5 组配置。 它们是 Skill、Tool、MCP Server、Planner 和实验。 存在会话 ID 时，再读取已保存的成功对话。 Planner 与 Skill 最多使用最后 8 条历史消息。

计划生成。 Planner 模型接收问题、历史和能力清单。 代码先检查必经能力是否可用。 预算或优惠意图由代码中的关键词规则识别。 模型的 needs_price 不决定是否强制插入计价工具。

计划重组。 模型候选需通过启用能力白名单。 无效、重复和必经项从动态候选中移除。 代码重新安排必经步骤，保留有效的可选能力。 risk-check 固定为最后一步。 因此，模型返回的步骤顺序不会被原样执行。

当前预算示例的必经顺序如下。 可选能力的位置由代码固定，内容由 Planner 选择。

顺序 能力 运行方式
1 need-extraction 模型提取需求，再由代码归一化
2 query_products 读取商品并筛选
3 query_activities 读取已启用活动
4 query_coupons 读取已启用优惠券
5 可选 Skill 或 Tool 例如办公室分享场景顾问
6 recommendation-decision 模型选择候选商品 ID
7 calculate_price 代码按选中商品计算价格
8 recommendation-reason 模型生成商品理由
9 response-generator 模型组织客服回复
10 risk-check 模型审核，并给出安全回复

没有可选能力时，上表对应 9 个执行步骤。 固定加入场景顾问的离线样例有 10 步。 该样例调用模型 7 次，包含 Planner 和 6 个 Skill。 Tool 的本地计算不调用模型。 MCP Tool 还会增加一次模型参数生成调用。

步骤之间通过内存 ctx 传递数据。 主要字段为 need、products、selectedProducts、price、reasons、reply 和 risk。 模型输出会接受基础类型与必填字段检查。 这不是完整的 JSON Schema 校验器。

依据：规划与组装，engine.ts:109、步骤执行，engine.ts:233、Planner 配置。

返回数据：每个字段是谁生成的

返回字段 数据来源 应如何理解
requestId 执行器生成 UUID 一次调用的标识；重跑会变化
sessionId 请求传入，或执行器生成 同一会话关联各轮调用
mode 代码固定为 ai 成功结果没有模拟模式分支
userInput 请求输入 主 Run 路由返回去空白后的文本
plan.goal、plan.reasoning Planner 模型；缺失时用代码默认值 reasoning 是可读摘要
plan.steps 模型候选经过代码重组 最终可执行能力清单
plan.decisionTrace 代码生成的 6 类规则事件 意图、可用性、规则、候选、过滤、组装
executionTrace 执行器逐步追加 步骤输入、输出、耗时和尝试次数
finalReply 代码从模型输出中选择 风控通过时取 reply，否则取 safe_reply
risk risk-check 模型输出 不是代码对答案正确性的独立证明
handoff 代码计算条件 建议转人工，不会自动提交人工队列
experiments 代码记录随机分流结果 当前只记录 Skill ID 与分支

若风控未通过且没有安全回复，代码使用固定兜底话术。 安全回复替换后，没有第二次风控调用。

接口没有顶层 products、price 或 need 字段。 商品原始结果应查 query_products 的轨迹输出。 价格原始结果应查 calculate_price 的轨迹输出。 最终回复文本中的价格，还经过话术模型组织。

decisionTrace 是规则执行摘要。 executionTrace 是业务步骤记录。 两者均不等于模型的隐藏思维链。

依据：结果组装，engine.ts:285、RunResult 与 TraceItem，types.ts:62。

Skill 参数与 Schema Skill 配置文件 提供模型、温度、上限和校验规则

订单物流与退货政策 本地订单和政策文件 当前没有连接真实物流或订单系统
推荐、理由、话术、风控 模型输出 依赖已提供上下文和指令约束
远端工具结果 已配置的 MCP Server 返回 content 与 structuredContent

Skill 指令来自文件，不是上传给模型后执行的本地脚本。 本地 Tool 按 Tool ID 进入硬编码分支。 修改 Tool 的 dataSource 描述，不会改变该分支。 MCP Tool 则先生成参数，再调用远端 tools/call。 本次配置快照包含 13 个启用 Skill、6 个本地 Tool。 MCP Server 数量为 0。

价格与筛选存在明确边界

商品预算筛选比较的是单件价格。 代码没有保证推荐组合总价不超过预算。 若没有筛选结果，代码回退到完整商品列表。 该回退会绕过原先的库存、口味和预算条件。

价格按每种选中商品各 1 件试算，不含运费。 需求中的 quantity 没有参与计价。 优惠券的 stackable 字段没有参与计算。

因此，代码算术正确与推荐满足需求是两个检查点。 风控仍由模型完成，不能替代组合预算的代码断言。

数据入口：商品、活动、优惠券、订单、政策。

实现依据：本地 Tool，engine.ts:168、Skill 加载，store.ts:58、MCP 调用，mcp.ts:78。

F

现有轨迹：怎样生成、失败和保存

每个步骤在最终成功或重试耗尽后追加一条记录。 记录包含步骤 ID、能力、类型、目的和状态。 还包含 input、output、startedAt、durationMs 和 attempts。 耗时覆盖该步骤的全部尝试。 中间失败尝试的错误与耗时没有分别保存。 类型定义虽含 running，执行器没有输出运行中事件。

分支 返回与记录 Agent 页实际展示
步骤全部完成 HTTP 200；返回完整业务步骤轨迹 展示轨迹、计划、最终回复
某一步重试耗尽 HTTP 500；trace 含成功前缀和失败步骤 只展示错误；failedTrace 未接入轨迹卡片
Planner 失败 HTTP 500；指标记为 Planner 失败 缺少轨迹、请求 ID 和会话 ID
风控未通过 HTTP 200；替换回复并建议转人工 显示“已修正”和人工审核按钮
配置读取或最终落盘失败 缺少统一的运行级失败封装 无法保证有轨迹和失败指标

运行完成不等于风控通过。 风控拒绝时，运行指标仍记为 success: true。 Planner 不在 executionTrace 中，也没有步骤级重试。

默认每个业务步骤最多尝试 2 次。 重试接口把上限改为 3 次。 点击重试会重新生成计划，不是从失败节点续跑。 重试没有错误分类、退避等待或幂等保护。

已验证：早期轨迹输入会被后续步骤改变

可选 Skill 的输入包含 context: ctx 引用。 调用时尚无 reply 字段。 整轮结束后，同一轨迹输入却出现了 reply。 离线验证结果为“调用时没有，返回时有”。 因此，这类输入不能当作调用当时的快照。

留存位置 保存内容 当前上限
