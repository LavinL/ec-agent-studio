技术架构：每层负责什么？

技术形态是 Next.js 全栈单体。 页面使用 React 客户端状态。 Route Handlers、Agent 执行和文件读写位于同一应用。 模型和 MCP 服务通过 HTTP 接入。

模块 职责 关键边界
app/*/page.tsx 输入、编辑、展示、发起请求 状态主要保存在 useState
app/api/ 参数接收、调用引擎、运营数据处理 大部分业务直接在处理函数中实现
lib/engine.ts 模型调用、计划组装、串行执行、计价 核心执行逻辑集中在一个文件
lib/store.ts Skill 装载、JSON 读写、版本与记录 以 process.cwd() 定位数据目录
lib/mcp.ts 初始化、工具发现、工具调用、关闭会话 自行实现 Streamable HTTP 客户端
lib/eval-seeds.ts 补充评测用例 运行时与本地用例合并
lib/types.ts 配置、Plan、Trace、评测与标注类型 主要约束 TypeScript 编译阶段

声明依赖包括 Next.js 15、React 19、TypeScript 和 Tailwind CSS 4。 当前安装版本为 Next.js 15.5.19、React 19.2.7、TypeScript 5.9.3。 本次验证使用现成的 Node.js 24.22.1。

Skill 的三个文件来源各司其职。

Skill 运行对象
skills/*/SKILL.mdname、触发描述、模型系统提示词
skills/*/agents/openai.yaml读取 display_name 作为界面名称
data/skills.json模型参数、启用状态、输入输出 Schema

Skill 的运行本质是一次结构化模型调用。 SKILL.md 正文进入 system message。 当前步骤输入序列化后进入 user message。 模型通过 chat/completions 返回 JSON。 系统没有装载 Skill 脚本、检索引用文件或执行嵌套工具的通用机制。

本地 Tool 按固定 ID 分支执行代码。 新增本地 Tool 需要修改执行代码和 API 白名单。 新增 Skill 可以被 Planner 选择，但其输出通常只进入 skillResults。 新增控制行为仍需要 Executor 显式处理。

MCP 扩展路径已经接入。 管理页调用 tools/list，把工具描述与 Schema 写入配置。 执行时，模型先生成参数，再调用 tools/call。 每次发现或调用都会新建并关闭 MCP 客户端会话。 Token 从服务端环境变量读取。

规划逻辑：模型决定哪些事，代码决定哪些事？

最终 Plan 由规则与模型候选共同组成。 模型主要补充可选能力。 必经 Skill、基础 Tool 和价格 Tool 来自配置。 核心顺序由 buildPlan() 重新构造。

阶段 实际逻辑 设计意图与限制
意图识别 对本轮原文做价格词正则匹配 发生在需求抽取之前；没有使用抽取结果
能力可用性 只向模型传递已启用 Skill 与 Tool 停用风控或缺少必经能力时直接失败
规则注入 基础 Tool 必选；价格意图追加价格 Tool 当前基础 Tool 固定包含商品查询
模型候选 返回目标、解释摘要和步骤列表 reasoning 是模型摘要，不是隐藏思维链
候选校验 校验类型、能力白名单和重复项 未验证步骤的数据依赖与业务前置条件
最终组装 首个必经 Skill → 查询 → 动态能力 → 后续必经 Skill risk-check 强制放在最后

默认价格任务形成以下顺序。

默认 Plan当前 planner.json 配置
  • 1 need-extraction模型抽取用户需求
  • 2 query_products本地查询候选商品
  • 3 query_activities仅价格意图强制加入
  • 4 query_coupons仅价格意图强制加入
  • 动态能力插槽模型选择的附加 Skill 或 Tool
  • 5 recommendation-decision模型选择商品 ID
  • 6 calculate_price在推荐决策之后插入
  • 7 recommendation-reason模型生成理由
  • 8 response-generator模型组织回复
  • 9 risk-check模型审核并提供修正版

没有动态能力时，价格任务为 9 步。 不触发价格规则时，默认路径为 6 步。 两种路径都包含 1 次 Planner 和 5 次核心 Skill 调用。 因此，无重试时的模型调用基数均为 6 次。 附加 Skill、MCP 参数生成、解释和 Judge 会增加调用。

这套骨架存在业务场景偏向。 物流与售后咨询也会经过商品查询和推荐步骤。 最终生成提示词要求隐藏无关推荐。 但前面的模型调用和数据处理仍然发生。 赠礼、过敏与澄清 Skill 在查询之后执行。 这些附加结果不会自动触发重新查询。

可配置顺序没有形成可靠的依赖约束。 计价只会被插到“后续必经 Skill”中的推荐决策之后。 把推荐决策移到首位，计价便不会被插入。 隔离验证中，强制 Tool 清单仍含计价，最终 Plan 却漏掉了它。

执行与数据：一次回答如何从输入走到输出？

请求先装载配置，再串行执行 Plan。 引擎按 sessionId 读取历史会话。 每个步骤共享一个内存 ctx 对象。 对话输入保留最近 8 条历史消息。 在正常问答中，这通常相当于最近 4 轮。

数据阶段 写入字段 下游如何使用
需求抽取 ctx.need 商品查询读取预算、口味与品类
本地查询 products、activities、coupons 决策与计价取得候选事实
附加能力 skillResults、toolResults、mcpResults 后续模型将其作为上下文
推荐决策 decision、selectedProducts 用候选商品过滤模型返回的 ID
价格计算 ctx.price 话术和风控引用计算结果
理由与话术 reasons、reply 组合答复并交给风控
风控审核 ctx.risk 通过时返回原回复，否则返回 safe_reply
运行结束 会话正文、指标、API 返回的 Trace 前端展示；评测运行另存完整结果

用当前商品数据走一遍。 输入为“预算 80 元，办公室分享咸口零食”。 隔离验证固定推荐 P001 与 P006。 这两个商品分别为海盐芝士小饼干、咸蛋黄糯米锅巴。

环节 确定的结果 事实来源
查询候选 P001、P006 都有“咸口”标签 products.json
商品金额 29.9 + 19.9 = 49.8 元 每款按 1 件计算
活动 未达到满 99 减 15；没有坚果折扣 activities.json
优惠券 未达到 59 元门槛；不满足坚果品类条件 coupons.json
最终试算 49.8 元，不含运费 calculate_price 输出

这个例子验证了工具运算路径。 推荐选择和模型输出使用固定返回值。 真实模型会选择哪些商品，本次没有验证。

计价规则可以直接从代码读出。 先合计已选商品，每款一件。 再选择单个活动，使活动后金额最低。 然后按活动后金额筛选券，选择减免额最大的券。 最终金额最低限制为零。 quantity、券的 stackable 和用户领券资格未参与计算。

失败处理是步骤重试和整轮重跑。 普通运行中，每步默认最多尝试 2 次。 重试 API 中，每步最多尝试 3 次。 重试使用同一 Plan，但没有持久化检查点。 失败达到上限后，返回部分 Trace 并结束整次请求。 模型与 MCP 请求没有显式超时或退避控制。

“转人工”目前是记录入口。 风控不通过或高风险时，引擎设置 handoff.required。 只有用户点击工作台按钮，才写入待处理记录。 当前没有受理、分派、人工回复和关闭的处理链路。 /ops 的人工评估处理质检样本，不消费这个接管队列。

普通运行的审计记录保存不完整。 会话文件保存消息正文，指标文件保存摘要。 完整 Trace 默认随响应返回，留在当前页面状态。 评测结果会另存 Trace；手动转人工也会保存传入的 Trace。 刷新页面后，工作台没有恢复原会话和执行详情的入口。

运营反馈：错误如何变成下一次改进？

这是有入口、有产物、靠人工接续的改进回路。

环节 已实现的连接 当前边界
收集评分 保存 QA 对和 1–5 分评分 1 分只取最后一个 QA 自动建标注
人工复核 汇总最新失败评测和未标注低分服务 已有标注的来源不再展示在复核候选中
标注 理想回复、事实、能力、禁用表述和六维评分 审核状态由页面直接选择
发布回归 仅 approved 标注可发布 Eval 理想回复进入 Judge 标准
执行评测 真实调用 runAgent，保存结果与 Trace 不写会话和线上运行指标
改进建议 规则汇总问题，再由模型生成 Prompt 建议 没有自动应用 Patch 的功能
配置变更 保存 Skill、Planner、Tool 或业务数据 保存即对后续运行生效
版本与实验 配置快照回滚，Skill 提示词随机分流 未绑定运行版本，也没有自动发布门槛

评测集有两个来源。 当前本地保存 23 条用例。 代码再补入 79 条种子，共得到 102 条可见用例。 这些数量描述配置规模，不代表本次已跑完真实模型回归。

评测分为六层。 无人工标注代理分时，总分公式为：

20%×Planner + 15%×Skill + 25%×Tool + 25%×回复 + 10%×风控 + 5%×性能

评分方法 实际计算方式 对总分的作用
精准匹配 忽略大小写和空白后做子串检查 影响关键点、能力和事实得分
余弦相似度 本地词袋或字符频次向量 仅诊断，不计入总分；没有使用向量模型
LLM-as-Judge 配置 Judge 标准后调用模型 占回复层 45%，其余 55% 为规则分
人工评估代理分 根据历史六维标注与当前错误扣分 存在六维标注时，占总分 10%

“人工评估代理分”由程序计算。 它不等于人工重新给当前回复打分。 页面概览仍写着人审不自动进机器分，与当前实现有出入。

通过条件是“总分至少 80，且没有硬失败”。 缺失能力、禁用能力、缺失事实和部分风控问题属于硬失败。 禁用表述、缺少回复关键词和延迟超限没有全部进入硬失败条件。 因此，存在发现问题但仍显示通过的情况。 具体复现见 G 面板。

Prompt A/B 目前只完成分流和记录。 每次执行 Skill 时，用 Math.random() 决定是否追加变体提示词。 分组不固定到会话，重试时也可能重新分配。 指标记录了变体，但没有实验效果对比和统计判定。 评测调用同样会读取当前已启用实验，结果未绑定完整配置版本。

演进顺序与验证依据

先让现有路径可信，再扩展更多能力。 以下是建议顺序，不是已经实施的修改。

顺序 目标 具体改动 可核验的完成标准
1 修正事实与验收 处理预算、数量、券规则、零匹配和评测硬失败 G 面板中的错误行为不再复现
2 建立任务状态 拆分推荐、物流、售后路径；增加澄清等待与人工受理状态 缺信息时暂停；接管后可受理并关闭

5 接通改进与发布 草案生成 Patch 预览；固定版本回归；审核后发布 每次变更都有对比证据和可回滚版本
6 完善实验与运行 固定会话分组、关联评分、记录用量；加入超时与重试策略 能计算效果差异、成本和任务完成率
